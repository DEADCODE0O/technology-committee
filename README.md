# منصة أنشطة اللجنة التكنولوجية — TECHNOLOGY COMMITTEE PLATFORM

منصة مجتمع طلابي متكاملة (Gamified Student Activity Platform): الموقع التعريفي الأصلي + نظام أعضاء + إدارة ورش + نقاط وإنجازات + لوحة إدارة مستقلة — بالعربية وRTL بالكامل، بنفس هوية Royal Black + Matte Gold.

---

## نظرة سريعة

| النظام | الوصف | الرابط |
|---|---|---|
| الموقع العام | الموقع الأصلي كما هو + الورش + المتصدرون + المواهب | `/` |
| منصة الطالب | تسجيل/دخول، داشبورد، حجز ورش، حضور QR، ملف شخصي | `/login` · `/register` · `/panel` |
| لوحة الإدارة | نظام مستقل بالأدوار: ورش، طلاب، نقاط، شارات، مواهب، إعدادات، سجل عمليات | `/admin` |

### المزايا الأساسية

- **حسابات الطلاب**: **Google OAuth أو بريد + كلمة سر عبر Supabase Auth** — الاسم/الفرقة/الشعبة/الجنس من قوائم جاهزة + بيانات تعارف وأسباب انضمام (التنسيق للفرقة الأولى فقط — مفروض على السيرفر)
- **الدخول بـ Google**: يُدار بالكامل من **Supabase Auth** — مستخدم Google الجديد يكمل بياناته الدراسية بصفحة مخصصة، ويمكنه لاحقًا تعيين كلمة سر للدخول بالبريد أيضًا (يُفعّل من لوحة Supabase وفق DEPLOY.md، وحسابات الإدارة بالبريد وكلمة السر فقط)
- **كود الطالب**: حقل جاهز + إعدادات لكل فرقة في الأدمن — **معطل افتراضيًا**، يفعّل بضغطة
- **دورة حياة الورشة**: مسودة → قادمة (تشويق مموه سينمائي) → جارية (تسجيل مفتوح) → منتهية (أرشيف) → مؤرشفة
- **Form Builder ديناميكي**: 11 نوعًا من الأسئلة لكل ورشة بدون كود، بما فيها رفع ملف (PDF/صورة)
- **التسجيل الذكي**: بيانات العضو تُجلب تلقائيًا + أسئلة الورشة فقط + **Waitlist** تلقائي بترقية فورية عند الإلغاء
- **تسجيل الضيوف (Guests)**: زائر بدون حساب يسجل في الورشة باسمه وهاتفه (مع أسئلة الورشة) — يظهر في المشاركين والحضور وملف Excel بشارة «ضيف» — يُتحكم به لكل ورشة من الأدمن. النقاط والشارات للأعضاء فقط
- **تسجيل يدوي (Manual)**: من الأدمن بدون إنشاء حسابات + تمييز المصدر في كل التقارير
- **صور الورش بـ 3 طرق**: مكتبة الصور الجاهزة · رابط خارجي · **رفع مباشر من الجهاز** (حتى 4MB — يُخزن في Supabase Storage عند النشر، ومحليًا في المعاينة)
- **الحضور منفصل عن التسجيل**: تحديد يدوي + **QR** لحضور ذاتي + تحديث لحظي
- **نظام النقاط المضاد للتلاعب**: كل نقطة حدث مسجل (من أضافها؟ لماذا؟ متى؟) — القواعد تتعدل من الأدمن بدون كود، والحضور يمنح النقاط تلقائيًا
- **Leaderboard**: الكلي + الشهر + الترم (فرصة دائمة للجدد)
- **الشارات والمواهب**: مواهب الطلاب مع توثيق وتمييز Featured من الإدارة
- **Excel**: تصدير المشاركين من الورش بفلاتر + تصدير قاعدة الطلاب كاملة بفلاتر (فرقة/شعبة/جنس/حضور/مواهب/نقاط وغيرها) + دعم Excel Template للورشة
- **سجل عمليات كامل (Audit Log)** لكل حركة إدارية
- **أدوار إدارية**: SUPER_ADMIN / ADMIN / WORKSHOP_MANAGER / CONTENT_MANAGER / VIEWER

### المزايا الجديدة (تحديث سبتمبر 2026)

- **إدارة المشرفين بصلاحيات دقيقة** `/admin/admins`: رقِّ أي طالب إلى مشرف (يحتفظ بحسابه وبريده) وحدد لكل وحدة صلاحيتها: إدارة / عرض / ممنوع / افتراضي الدور — مع تنزيله لطالب أو تعليقه أو إعادة تعيين كلمة سره
- **طلبات البيانات الموجهة** `/admin/data-requests`: أنشئ نموذجًا مخصصًا (11 نوعًا من الأسئلة) ووجهه لمجموعة بدقة — فرقة / شعبة / جنس / حاضرين وغير الحاضرين / الموهوبين / المتفوقين (نقاط ≥) / طلاب بعينهم — يظهر للطالب المستهدف في لوحته مع موعد نهائي اختياري، وتُعرض الاستجابات في جدول للإدارة
- **تعديل كامل بيانات الطالب من الإدارة**: الاسم والهاتف والفرقة والشعبة والجنس والكود **وحتى البريد وكلمة السر** — كل التعديلات موثقة
- **تصنيف الطلاب في صفحتهم**: فلاتر الفرقة / الشعبة / الجنس / الحالة / الحضور / المواهب / المتفوقين (نقاط ≥) + البحث الشامل
- **النقاط الجماعية**: منح أو خصم نقاط لمجموعة مستهدفة دفعة واحدة (مكافأة تفوق، خصم غياب...) + **حذف الأحداث الخاطئة** بسبب موثق
- **واجهة الطالب الموحدة**: شريط تنقل سفلي ثابت للموبايل (لوحتي / الورش / المتصدرون / ملفي) مثل التطبيقات + شارة عداد لطلبات اللجنة المنتظرة + تصميم متجاوب بالكامل
- **الشعبة إلزامية لضيوف الورش** — تُطلب في نموذج الضيف وتُخزن مع تسجيله

### المزايا الجديدة (تحديث سبتمبر 2026 — الجولة الثانية)

- **الطلبات الإلزامية (بوابة الدخول)**: عند إنشاء طلب بيانات فعّل خيار «إلزامي» — الطالب المستهدف يُحوَّل فور فتحه المنصة إلى صفحة «البيانات المطلوبة» ولا يدخل لوحته (ولا يستطيع أي عملية) حتى يسلّمها. الطلب الاختياري يظهر بشكله العادي في لوحته
- **كود الطالب يُطلب داخل المنصة**: لو فعّلت الأكواد لفرقة بعد تسجيلهم، مين سجّل الكود منهم تطلبه منه المنصة فور دخوله (نفس البوابة) — مش فقط وقت التسجيل
- **خصم نقاط صريح + تراجع**: في نافذة نقاط أي طالب زرّا «منح / خصم» واضحان، وفي سجل النقاط زر «تراجع» ينشئ حدثًا معاكسًا يلغي أي منح أو خصم سابق مع بقاء التاريخ موثقًا
- **نظام التراجع الشامل**: كل عملية إدارية (28 نوعًا — ورش، نقاط فردية وجماعية، قواعد، شارات، مواهب، بيانات طلاب، مشرفين وصلاحيات، حضور، تسجيلات وإلغاءات وترقيات، طلبات بيانات، إعدادات) تخزن نسختها «قبل التنفيذ» في سجل العمليات — من صفحة السجل اضغط زر التراجع بأي عملية (حتى اللي عملها مشرف آخر) وستعود الحالة كما كانت، والتراجع نفسه يُوثَّق ولا يمكن التراجع عن العملية مرتين
- **زر الانضمام صار للتسجيل**: «سجّل في المنصة الآن» في الرئيسية وقسم التسجيل يقودان مباشرة لصفحة إنشاء الحساب
- **تسجيل أسهل من الهاتف**: أزرار المعالج الثابتة أسفل الشاشة (في متناول الإبهام) + إظهار/إخفاء كلمة السر + لوحة أرقام للهاتف والكود
- **تجاوب محصّن**: إصلاح جذري لمشكلة تضخّم الشبكات على الموبايل (كانت تكسر صفحة الورشة) وتحصين كل شبكات الموقع — صفر تمرير أفقي على كل الصفحات بعرض 390px

### الجولة الثالثة — تجهيز الإنتاج (Production Hardening)

- **صفر تجاهل لأخطاء TypeScript**: أُزيل `ignoreBuildErrors` وفُعِّل `noImplicitAny` — البناء يفشل عند أي خطأ نوع (وإعدادات البناء تمنع تجاهل أخطاء TypeScript)
- **React Strict Mode** مفعّل — كشف مبكر للمشاكل
- **تسجيل Prisma حسب البيئة**: إنتاج = أخطاء وتحذيرات فقط (استعلامات SQL عند الحاجة عبر `PRISMA_LOG_QUERY=1`)
- **حماية الجلسات**: الخادم يرفض العمل في الإنتاج بدون `AUTH_SECRET` قوي (32+ حرفًا) — لا سر افتراضي أبدًا
- **محدد معدل (Rate Limiting)**: دخول (8 محاولات/بريد + 25/IP كل 15 دقيقة مع تصفير عند النجاح) + تسجيل (20/ساعة) + ضيوف (10/ساعة) — رسائل عربية واضحة
- **رفع الصور محصّن**: مسار `/api/admin/upload` مع فحص البصمة الفعلية للملف (Magic Bytes) + الحجم + اسم مولّد آمن + Supabase Storage عند النشر
- **رؤوس أمنية موحدة**: `X-Content-Type-Options` + `X-Frame-Options` + `Referrer-Policy` + `Permissions-Policy`
- **فهرسة قاعدة البيانات**: فهارس إضافية للبحث السريع (هاتف، كود الطالب، تسجيلات الطالب، سجل العمليات بالكيان)
- **Seed بوضع الإنتاج**: `SEED_PRODUCTION=1` ينشئ SUPER_ADMIN فقط من متغيرات البيئة — بدون أي بيانات تجريبية في الإنتاج
- **فحص صحة موحد** `/api` + إصلاح `metadataBase` للـ SEO + `.env.example` شامل لكل المتغيرات

### الجولة الرابعة — Supabase Auth (البنية الرسمية للإنتاج)

تحوّل البنية التحتية للإنتاج إلى **Supabase بالكامل** (بلا أي تغيير في الواجهات أو منطق العمل):

- **Supabase PostgreSQL** هي قاعدة الإنتاج الوحيدة عبر Prisma (`DATABASE_URL` = Session pooler للتشغيل + `DIRECT_URL` للاتصال المباشر والترحيلات) — أُزيلت كل إشارات Neon
- **Supabase Auth هو نظام المصادقة الرسمي**: بريد + كلمة سر (signUp/signInWithPassword)، جلسات عبر `@supabase/ssr` بكوكيز httpOnly + Middleware يحدّث الجلسات قبل انتهائها
- **Google OAuth عبر Supabase Auth** (بدل التنفيذ اليدوي السابق): زر Google يستدعي `signInWithOAuth` ويعود إلى `/auth/callback` (PKCE) — ربط الحسابات بالبريد الموثق أو googleId، ومنع دخول الإدارة عبر Google كما هو
- **الهوية UUID من `auth.users`**: صف المستخدم يُنشأ بنفس UUID الرسمي، وكلمات السر لا تُخزن في قاعدة بيانات التطبيق إطلاقًا
- **استعادة كلمة السر بالبريد**: صفحتا «نسيت كلمة السر» و«تعيين كلمة جديدة» عبر `resetPasswordForEmail` — رابط «نسيت كلمة السر؟» في صفحة الدخول
- **تفعيل البريد**: إعداد Supabase يحدد هل يحتاج الطالب تأكيد البريد قبل الدخول؛ الواجهة تتعامل مع الوضعين تلقائيًا
- **الهاتف**: رقم الهاتف جزء من الملف ويُطلب عند التسجيل؛ SMS OTP مؤجل لمرحلة لاحقة حتى تظل النسخة المجانية بلا تكلفة رسائل.
- **إدارة كلمات السر من اللوحة**: إعادة تعيين كلمة سر مشرف/طالب وتغيير البريد تعمل عبر Supabase Admin API (service_role — سيرفر فقط)
- **RLS جاهز**: ملف `supabase/rls.sql` بسياسات عزل بيانات الطلاب (كل طالب صفه فقط) — طبقة دفاع ثانية اختيارية
- **مصدر المصادقة في الإنتاج**: Supabase Auth، مع Google OAuth أو Email/Password؛ PostgreSQL هو مخزن البيانات الرئيسي.

## جاهزية التطبيق المحمول لاحقًا

الموقع هو الواجهة الأولى فقط؛ منطق الأعمال الأساسي موجود في Server Actions وواجهات API ويستخدم PostgreSQL كمصدر حقيقة، لذلك يمكن بناء تطبيق Flutter/React Native لاحقًا فوق نفس طبقة الخدمات دون نسخ قواعد التسجيل أو النقاط أو الحضور داخل التطبيق. بيانات التطبيق ستبقى مشتركة مع الموقع، وتُفرض الصلاحيات من السيرفر.

## التشغيل المحلي

المتطلبات: Node.js 18.18+ (أو Bun). النسخة الحالية تستخدم نفس مخطط PostgreSQL/Supabase في التطوير والإنتاج لتقليل فروق البيئة. (للتطوير دون اتصال بـ Supabase يتوفر وضع معاينة محلي: `npm run db:use-sqlite` ثم `DATABASE_URL="file:./db/custom.db"`.)

```bash
# 1) التثبيت
bun install        # أو npm install

# 2) أنشئ .env من .env.example ثم أضف بيانات Supabase

# 3) إنشاء عميل Prisma وتطبيق الترحيلات
bun run db:generate
bun run db:migrate:deploy

# 4) (اختياري) بيانات أولية
bun run db:seed

# 5) التشغيل
bun run dev        # أو npm run dev
```

> الأفضل أن تستخدم مشروع Supabase تطويريًا منفصلًا عن الإنتاج حتى تبقى بيانات الطلاب الحقيقية معزولة.

## النشر المجاني (Vercel + Supabase)

دليل كامل خطوة بخطوة في ملف **[DEPLOY.md](./DEPLOY.md)** — التكلفة 0 جنيه.

خلاصته:
1. GitHub → رفع المستودع (خاص)
2. Supabase → قاعدة PostgreSQL مجانية (500MB) + Storage للصور (1GB) + bucket باسم `workshops`
3. `npm run db:migrate:deploy` لتطبيق migrations على Supabase
4. Vercel → Import + متغيرات البيئة → Deploy
5. `db:seed` لتهيئة الإعدادات وقواعد النقاط والشارات
6. فعّل Google OAuth من Supabase Authentication → Providers
